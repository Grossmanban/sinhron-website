Как Sinhron устроен изнутри: из каких частей состоит, как по ним путешествует сообщение и звонок и на каких стандартах всё держится. Страница для тех, кому интересно заглянуть под капот, — разработчиков, владельцев серверов и проверяющих.

Устройства общаются только с вашим сервером. Push-уведомления, когда они будут подключены, пойдут через Apple и Google — но без содержимого.

## Клиент: Flutter и Rust

Клиент состоит из двух слоёв.

**Flutter UI** — интерфейс на Dart: экраны, анимации, навигация. Одна кодовая база на пять платформ и собственная дизайн-система вместо стандартных виджетов Material.

**Rust Core** — всё остальное: криптография, локальная база, сеть и логика синхронизации. Flutter общается с ним через `flutter_rust_bridge`, который генерирует связку между Rust и Dart автоматически. Core состоит из нескольких крейтов:

| Крейт | Что делает |
|---|---|
| `sinhron_crypto` | ключ из 24 слов (BIP-39), вывод ключей, подписи, обёртки над OpenMLS |
| `sinhron_storage` | локальная база SQLite, целиком зашифрованная SQLCipher |
| `sinhron_net` | WebSocket и HTTPS-клиент, TLS, переподключения, прокси SOCKS5 (Tor) |
| `sinhron_sync` | синхронизация MLS, формат сообщений, запечатанные конверты, привязка устройств, медиа, резервная копия |
| `sinhron_call` | ключи SFrame и состояние звонка |
| `sinhron_core` | фасад, который видит Flutter |

Главное правило: приватные ключи создаются и используются только в Rust. В Dart попадает то, что нужно показать на экране; кроме того, Dart передаёт ключ устройства на хранение в Keychain, а для звонка — ключи SFrame в SDK LiveKit, где они живут только в памяти.

## Сервер

`sinhron-server` написан на Rust (Axum и Tokio) и хранит данные в PostgreSQL 16. Сервер намеренно «глупый»: он не умеет расшифровывать и ничего не знает о содержимом.

- **WebSocket** `/v1/sync` — основной канал: отправка и получение зашифрованных сообщений, подтверждения, возобновление после обрыва, сигналинг звонков. Кадры — Protobuf.
- **HTTPS** — регистрация аккаунтов и их устройств, передача запечатанного пакета при привязке устройства по QR, публикация KeyPackage и ключей доставки, приём запечатанных конвертов без входа в аккаунт, зашифрованная резервная копия, загрузка и скачивание файлов, выдача пропусков для звонков.
- **Хранение.** Сообщения — шифротекст, по умолчанию 14 дней (для тех, кто был офлайн). Файлы — шифротекст на диске, имя — SHA-256 содержимого, удаляются через 90 дней без обращений.
- **Служебное.** Проверки `/_healthz` и `/_readyz`, метрики Prometheus, лимиты частоты запросов.

Каждый запрос, который что-то меняет, подписан ключом пользователя — паролей нет вовсе.

## Как доходит сообщение

1. **Знакомство.** Чтобы начать чат, приложение Алисы берёт с сервера KeyPackage Боба — заранее опубликованный «ключ для приглашения» — и создаёт группу MLS. Боб получит приглашение (Welcome), даже если сейчас не в сети.
2. **Упаковка.** Алиса пишет сообщение. Rust Core упаковывает текст вместе с ответом, форматированием или таймером исчезновения, дополняет до кратного 512 байтам и шифрует ключом текущей эпохи группы.
3. **Запечатывание.** Если получатели опубликовали ключи доставки, Rust Core кладёт MLS-сообщение в отдельный запечатанный конверт (HPKE) для каждого получателя — сервер не узнает, к какому чату оно относится. Иначе сообщение уходит как есть.
4. **Отправка.** Шифротекст с уникальным идентификатором уходит на сервер. Если у приложения есть ключи доступа всех участников чата, запечатанные конверты идут по HTTPS без входа в аккаунт, иначе — по WebSocket вошедшей сессии. Если включён прокси, и то и другое идёт через него.
5. **Хранение и рассылка.** Сервер сохраняет шифротекст в PostgreSQL и рассылает его всем устройствам получателей, которые сейчас на связи, — в том числе другим вашим устройствам, если их несколько. Запечатанный конверт хранится только для своего получателя, без связи с чатом.
6. **Офлайн.** Если Боб не в сети, сообщение ждёт его на сервере. При подключении приложение сообщает, что получило последним, и сервер досылает недостающее.
7. **Расшифровка.** Rust Core у Боба вскрывает конверт, если он есть, проверяет подпись Алисы, расшифровывает сообщение, отбрасывает дубликаты и сохраняет его в зашифрованную базу. Интерфейс показывает текст.
8. **Квитанции.** Отчёт о доставке и прочтении — это ещё одно зашифрованное сообщение, для сервера неотличимое от обычного.

**Файлы** идут чуть иначе: приложение шифрует файл случайным ключом (AES-256-GCM), загружает шифротекст по HTTPS, а ключ и хеш отправляет внутри зашифрованного сообщения.

## Как устроен звонок

1. **Вызов.** Алиса нажимает «Позвонить». Приглашение, ответ и завершение звонка идут по тому же WebSocket.
2. **Пропуска.** Сервер проверяет, что каждый участник звонка состоит в чате, и выдаёт ему токен LiveKit и временные данные для TURN.
3. **Подключение.** Устройства подключаются к LiveKit по `wss://`, а медиа идёт по WebRTC: напрямую по UDP или TCP либо через coturn, в том числе по TLS на порту 443.
4. **Ключи.** Каждое устройство само выводит ключи SFrame из группы MLS этого чата (RFC 9605, §5.2): у каждого участника свой ключ, а общий секрет группы позволяет всем вывести ключи друг друга, ничего не передавая по сети.
5. **Разговор.** Каждый кадр звука и видео шифруется SFrame на устройстве. LiveKit пересылает зашифрованные кадры и не может их прочитать.
6. **Смена ключей.** Если ключи группы меняются, ключи звонка обновляются вслед за ними, а старые удаляются из памяти.

Звонить можно и в личном чате, и в группе. Групповой звонок возможен в чатах до 32 человек: приглашаются все остальные участники, присоединиться можно и позже, а звонок идёт, пока в нём больше одного человека. Групповые звонки сделаны, но на реальных устройствах ещё не проверялись.

## Стандарты

Sinhron не изобретает криптографию, а опирается на открытые стандарты:

- [RFC 9420 — Messaging Layer Security (MLS)](https://www.rfc-editor.org/rfc/rfc9420) — сквозное шифрование переписки в группах любого размера.
- [RFC 9605 — Secure Frame (SFrame)](https://www.rfc-editor.org/rfc/rfc9605) — шифрование аудио- и видеокадров в звонках через медиасервер.
- [BIP-39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki) — фраза из 24 слов, из которой выводятся ключи аккаунта.
- [RFC 9180 — Hybrid Public Key Encryption (HPKE)](https://www.rfc-editor.org/rfc/rfc9180) — гибридное шифрование открытым ключом: на нём строятся MLS, конверты «запечатанного отправителя», скрывающие чат, и передача ключей новому устройству при привязке по QR.
- [RFC 5869 — HKDF](https://datatracker.ietf.org/doc/html/rfc5869) — вывод ключей из общего секрета.
