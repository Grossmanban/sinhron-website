No messenger protects against everything. A threat model is an honest description of who might attack you, what Sinhron does about it, and where its protection ends. This page is a plain-language summary of the project's internal threat model.

## Why a threat model

Security claims are only useful if you know their limits. "End-to-end encrypted" says a lot about message content, but very little about metadata, a stolen phone or a compromised server. By writing down what we defend against and what we do not, we want to help you decide whether Sinhron fits your situation, and help reviewers hold us to our word.

Sinhron is built for **personal, family and team privacy**. It is not designed to withstand a determined state-level adversary, and it has not yet been independently audited.

## What we protect against

**Someone watching the network.** Your internet provider, a public Wi-Fi operator or anyone in between sees only encrypted TLS connections. Inside them, messages are encrypted again with MLS. For extra protection, a server operator can pin their own certificate authority into the app, so that even a fraudulent certificate from a compromised public authority will not be accepted.

**A compromised or curious server.** This is the central design goal. Even someone with full access to the server and its database dump gets only encrypted messages, encrypted attachments and an encrypted backup they cannot open. They cannot forge messages, because every message is signed by its sender and checked by the recipients. They cannot add themselves to a call, because call access is only granted to members of the chat.

**Push notification providers.** Apple and Google deliver notifications, so they never receive message text, sender names or chat identifiers. Notifications only say that something new has arrived.

**A malicious or removed group member.** Only current members of a chat can read it. When someone is removed, the keys change and they cannot read anything sent afterwards. Thanks to forward secrecy, a key leaked today does not reveal yesterday's messages, and thanks to post-compromise security, a group recovers after a device compromise once keys are refreshed.

**A lost or stolen phone.** The local database is encrypted with SQLCipher, and you can turn on app lock with Face ID, Touch ID or your passcode. Decrypted photos and videos are kept in memory rather than saved to disk.

**Impersonation.** You can compare a 60-digit safety number with each contact, in person or by scanning a QR code. If their key ever changes, Sinhron warns you.

**Call eavesdropping.** Calls are end-to-end encrypted with SFrame, using keys derived from the chat's MLS keys. The call server forwards frames it cannot decrypt. Any tampering with encrypted frames is detected and rejected.

**Abuse of the server.** Registration, message sending and uploads are rate-limited, and the relay server for calls cannot be used as a general-purpose proxy.

## What's out of scope

Some threats are beyond what any app can solve, or beyond what Sinhron currently aims for:

- **State-level adversaries** who can compel server operators, observe networks at scale, or buy zero-day exploits.
- **A compromised device.** If your phone's operating system is compromised, or someone has physical access to it while it is unlocked, they can see what you see.
- **The people you talk to.** A chat partner can always take a screenshot, photograph the screen or forward what you wrote. Encryption cannot stop that, and neither can disappearing messages.
- **Social engineering.** If someone tricks you into revealing your 24-word key, they can take over your account.
- **Network-level anonymity.** Sinhron does not hide your IP address from the server. If you need that, you can combine it with other network tools.
- **Root access to the server.** An attacker who controls the server machine can disrupt service, tamper with the server software and see metadata. They still cannot read message content, but the operator is responsible for keeping the machine secure.

## Known limitations today

We prefer to list these openly:

1. **No independent security audit yet.** One is planned before a public launch.
2. **Metadata is visible to the server.** The operator can see who talks to whom, when, and approximately how much, as well as IP addresses. See [What the server sees](/docs/security).
3. **Sealed sender is only partial.** The server can currently tell which device sent a message. Fully hiding the sender requires an extra encrypted envelope (based on HPKE, RFC 9180), which is not built yet.
4. **Size and timing patterns.** Messages are padded to 512-byte buckets and attachments are padded too, but there is no cover traffic. Read receipts and typing indicators are also encrypted messages, so they add to the visible traffic pattern. During calls, packet sizes and timing can reveal when someone is speaking.
5. **Call metadata.** The call server sees who joined a call, when and from where.
6. **One device per account.** Linking several devices is not available yet.
7. **Incoming calls only while the app is open,** and push notifications are not enabled yet. Both need an Apple developer certificate.
8. **iOS file protection class is not set yet.** The database is encrypted with SQLCipher, but the extra iOS data protection level for files is still on the to-do list.
9. **Short-lived temporary files.** Sharing a file, recording a voice message or picking a file from your library briefly creates a temporary file, which is deleted right after. Voice messages are played through a local-only connection on the device while they play.
10. **Link previews reveal the sender's IP** to the website, if you turn them on. They are off by default, and recipients never contact the website.
11. **Pending invitations.** When you add someone who is offline, the encrypted invitation waits on the server for up to 7 days.
12. **No reproducible builds yet,** so you cannot yet independently verify that a published app was built from this exact source code.
13. **Media and calls on real devices.** Media is not yet verified on a real device, and calls across different networks have not yet been fully tested on a deployed server.

## Reporting a vulnerability

If you find a security problem, we would be grateful to hear about it.

- Open an issue on [GitHub](https://github.com/Grossmanban/sinhron-website/issues), or contact the maintainers through their GitHub profiles.
- If the problem is serious and could put users at risk, please do not publish exploit details in a public issue. Open an issue asking for a private channel, or reach out to the maintainers directly through GitHub, and we will take it from there.
- Please include the version or commit you tested, steps to reproduce, and what you expected to happen.

Thank you for helping keep Sinhron and its users safe.
